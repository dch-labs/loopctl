## [0.6.0] - 2026-11-18

### Changed

- **`rusqlite` 0.41 → 0.42 — a dependency bump that is semver-breaking for one exposed type, so consumers move with it** — the requirement moved (`rusqlite = "0.42"`, `bundled` as before) with no code change: the store compiles and its whole suite passes unchanged on 0.42. The one consumer-visible seam: `SqliteMemoryError::Sqlite` carries `rusqlite::Error` verbatim (the `#[from]` variant the constructors' errors ride), and on native targets a straddling graph does not degrade — it refuses to resolve: rusqlite 0.41 requires `libsqlite3-sys ^0.39` while 0.42 requires `^0.40` (disjoint ranges), and every `libsqlite3-sys` version declares the same `links = "sqlite3"`, so cargo rejects the dependency graph outright (`failed to select a version for libsqlite3-sys`) rather than linking two copies of the native library. The refusal is not confined to hosts that name `rusqlite` directly: a transitive path to another native SQLite dependency that cannot resolve to the same compatible `libsqlite3-sys` package — an older `rusqlite` still requiring `^0.39`, for one — hits the same links refusal through no choice of the consumer; a dependency whose range admits `^0.40` unifies onto the one package and does not conflict. Nothing in-repo coordinates against the crate (the `loopctl-vector` companion and every example are rusqlite-free), so the move is consumer-side only. **Migration:** align every direct and transitive native SQLite dependency before upgrading — a host keeping its own `rusqlite` moves it to `0.42` (matching arms over `SqliteMemoryError::Sqlite(e)` and conversions from `rusqlite::Error` follow the same version); a consumer whose graph touches no other native SQLite is unaffected, and the `bundled` SQLite build rides along.

## [0.4.0] - 2026-10-10

### Added

- **`SqliteMemoryStore`** — a persistent [`LoopMemory`](https://docs.rs/loopctl/latest/loopctl/memory/trait.LoopMemory.html) backend over a local SQLite database (WAL journaling, `NORMAL` sync — committed transactions survive a process crash, but the most recent commits may be lost to power loss — five-second busy timeout; `rusqlite` with the `bundled` feature so no system SQLite is required). Every [`MemoryEntry`](https://docs.rs/loopctl/latest/loopctl/memory/struct.MemoryEntry.html) field round-trips — `SystemTime` stamps at millisecond resolution (sub-millisecond precision is truncated), tags as a JSON text column, `relevance` on the `REAL` column, and a foreign out-of-range `access_count` is rejected on load as corruption (`InvalidEntry`, like a malformed id or category) rather than loading a plausible value, while a non-finite `relevance` is rejected loudly at `store` time (SQLite stores NaN as `NULL` against the `NOT NULL` column — the same refuse-the-input class the file backend guards before its append) — and memory survives a process restart by reopening the same file. Retrieval loads every entry and ranks it in Rust with loopctl's shared `score_entry` — the same entries match, in the same order with the same tie-breaking, as `InMemoryStore`/`FileMemoryStore`, except duplicate-id stores, where the core `INSERT OR REPLACE` keeps the newest single copy while the flat backends append and keep both; an FTS5 (`porter unicode61`) index is maintained on every write but not consulted by retrieval — ranking every entry is what guarantees the parity contract. Retrieval stamps land in a durable `access_stamps` table (upsert, newest-wins) rather than per-instance memory, so they are shared across every store instance on the same file and survive a restart; `consolidate()` consumes every pending stamp inside its transaction (fold, then decay, merge, prune via loopctl's shared pass) and rewrites the table and the full-text index in that same transaction — a stamp is either folded by a pass or survives as a row for the next one, never lost to a retrieve racing a consolidate. Multi-process concurrency: open several stores against the same file — WAL coordinates them. Version-pinned to `loopctl` (`=0.4.0`) until the trait surface stabilizes. Pinned by `opening_an_existing_database_is_idempotent`, `entries_survive_a_restart_with_every_field_intact`, `retrieval_ranks_full_text_matches_first`, `retrieval_respects_the_limit`, `consolidation_prunes_and_the_delete_is_durable`, `len_counts_rows_and_respects_deletes`, `two_stores_on_one_file_coordinate_through_wal`, and `an_in_memory_database_round_trips_without_the_filesystem`, `consolidates_racing_retrieves_never_lose_a_stamp`, `all_three_backends_rank_identically_including_ties`, `duplicate_id_stores_collapse_to_one_copy_here_but_not_in_the_file_store`, and `decode_entry_rejects_a_negative_access_count`.
